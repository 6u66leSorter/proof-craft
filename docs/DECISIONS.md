## Зафиксированные решения

### 2026-09-22 — Prisma baseline не управляет схемой legacy SQLite

- **Контекст:** NestJS должен читать существующую БД до переноса всех writers, а структура SQLite пока создаётся и мигрируется `bot/database.js`.
- **Решение:** Prisma 7.10 интроспектирует временную БД и работает через repository boundary; `db push` и Prisma migrations запрещены до отдельного cutover схемы.
- **Причина:** два независимых механизма миграций на одной production-БД создают риск несовместимой структуры и необратимых изменений.
- **Последствия:** drift между legacy и Prisma проверяет e2e-тест по всем 19 таблицам. Физические имена и legacy-типы пока сохранены; runtime требует явный абсолютный SQLite `DATABASE_URL`.

### 2026-09-22 — NestJS использует Fastify adapter и отдельный пакет

- **Контекст:** новый backend должен некоторое время работать рядом с legacy Fastify и постепенно принимать маршруты с файлами и streaming.
- **Решение:** разместить NestJS в независимом `backend/`, использовать официальный Fastify adapter и порт `8788` по умолчанию; legacy остаётся на `8787`.
- **Причина:** отдельные зависимости и сборка уменьшают влияние на действующий клиент и API, а общий HTTP-движок упрощает последующий перенос multipart и файловых ответов.
- **Последствия:** маршруты переключаются точечно; весь `/api` нельзя направлять в Nest до завершения миграции. Prisma добавляется следующим отдельным этапом.

### 2026-09-22 — Пошаговая миграция backend на NestJS и Prisma

- **Контекст:** legacy API объединяет 58 Fastify-маршрутов, синхронный SQLite, файлы, авторизацию, Telegram/VK и бизнес-логику; Telegram-бот напрямую изменяет ту же БД.
- **Решение:** сначала зафиксировать контракты и дефекты characterization-тестами, затем поднять NestJS рядом и переносить маршруты по одному. Prisma сначала подключается к существующей SQLite; переход на PostgreSQL выполняется отдельно после прекращения прямых legacy-записей.
- **Причина:** одновременная смена HTTP-фреймворка, ORM и СУБД не позволяет надёжно локализовать регрессии и усложняет откат.
- **Последствия:** внешние URL и форма ответов сначала сохраняются; небезопасные legacy-дефекты явно перечислены в `docs/migration/BEHAVIOR_DECISIONS.md` и не считаются обязательной совместимостью.

### 2026-09-20 — Фотография профиля ученика видна другим ролям

- **Контекст:** ученик загружал аватар, но его видел только он сам: файл отдавался единственным endpoint'ом `/api/student/me/avatar`, а у преподавателя, администратора и гостя в шапке профиля стояла демонстрационная фотография постороннего человека.
- **Решение:** добавить `/api/students/:id/avatar` для ученика, его преподавателей и администратора и публичный `/api/guest/students/:id/avatar` для витрины; во все ответы с данными ученика добавить `has_avatar`.
- **Причина:** портфолио теряет смысл, если работу показывает человек без лица, а вместо ученика видно чужое демо-фото.
- **Последствия:** фотография ученика со статусом `studying` становится публично доступной без авторизации — это часть гостевой витрины, как и его имя, метро и работы. Гостевой ответ кэшируется как `public`, ролевой — как `private`. Если ученик аватар не загрузил, интерфейс показывает прежнюю заглушку (инициалы или демо-фото).

### 2026-09-20 — Переменные окружения API перечисляются в ecosystem.config.cjs явно

- **Контекст:** `.env` на сервере содержал `TG_WEBAPP_AUTH=strict`, но API работал в режиме `optional`, потому что не читает `.env` сам.
- **Решение:** все переменные, нужные процессу `barber-api`, перечислять в блоке `env:` файла `ecosystem.config.cjs`, а не полагаться на передачу окружения через PM2.
- **Причина:** `apiServer.js` не импортирует dotenv, а неявная передача окружения зависит от состояния демона PM2 и флага `--update-env`, то есть ненадёжна.
- **Последствия:** при добавлении переменной для API её нужно прописывать и в `.env`, и в `ecosystem.config.cjs`. Проверять фактическое окружение процесса можно чтением `/proc/<pid>/environ`.

### 2026-09-14 — Роли, уровни обучения и публичная витрина

- **Контекст:** нужен единый сайт с разными правами и наглядным разделением пути ученика.
- **Решение:** сайт открывает обычный вход через Telegram/VK для ученика, преподавателя и администратора; гость открывает публичную витрину по ссылке без авторизации. Учеников разделяют уровни «Ученик», «Стажёр», «Барбер».
- **Причина:** это отделяет публичное портфолио от учебных данных и облегчает навигацию в больших списках.
- **Последствия:** контакты, никнеймы и служебные идентификаторы не передаются гостю. Администратор назначает уровень; при уровне «Барбер» все привязки к преподавателям автоматически снимаются. При возврате в обучение преподавателя назначают заново.

### 2026-09-14 — Конфиденциальная обратная связь ученика

- **Контекст:** ученику нужен безопасный канал для пожеланий о преподавателе и академии.
- **Решение:** отзыв отправляется отдельной формой и доступен только ученику при отправке и администраторам при просмотре. После принятия уроков 5, 10 и 15 бот приглашает ученика оставить отзыв.
- **Причина:** преподаватель не должен получать текст или уведомление об отзыве, чтобы ученик мог говорить открыто.
- **Последствия:** отзывы не являются анонимными для администратора: он видит автора. Таблицы `private_feedback` и `feedback_invites` не использовать как часть чатов или портфолио.

### 2026-09-07 — Самостоятельный вход на сайт через Telegram или VK

- **Контекст:** дневник должен работать как обычный сайт, без обязательного постоянного запуска из Telegram или VK Mini App.
- **Решение:** на сайте показать два входа: Telegram и VK. Пользователь подтверждает одноразовый запрос в выбранной платформе, после чего возвращается к обычному сайту с серверной веб-сессией.
- **Причина:** не нужны SMS, пароль и отдельный новый аккаунт; используются уже связанные учётные записи академии.
- **Последствия:** перед production-запуском задать `TELEGRAM_BOT_USERNAME`, включить `TG_WEBAPP_AUTH=strict`, настроить VK Mini App и его серверную подпись. Пользователь, у которого Telegram и VK ещё не связаны, входит через исходную платформу либо связывает аккаунты существующим сценарием.

### 2026-09-07 — Локальный браузерный предпросмотр без платформы

- **Контекст:** основной интерфейс блокирует обычный браузер, потому что ждёт запуск из Telegram или VK.
- **Решение:** в Vite-разработке параметр `?preview=1` использует отдельный тестовый идентификатор и открывает экран регистрации/гостевой раздел.
- **Причина:** это позволяет посмотреть интерфейс локально, не подставляя реальные аккаунты и не меняя production-авторизацию.
- **Последствия:** для данных нужен локальный API; его режим без Telegram-авторизации допустим только для временной локальной разработки.

### 2026-09-06 — Постоянная память проекта хранится в репозитории

- **Контекст:** нужно сохранять важный контекст между задачами, не перечитывая весь код.
- **Решение:** использовать `PROJECT_CONTEXT.md`, этот журнал, `WORK_LOG.md`, `QUALITY_RULES.md` и правила в `AGENTS.md`.
- **Причина:** документы доступны при следующей задаче, проверяемы и обновляются вместе с проектом.
- **Последствия:** существенные решения и завершённые задачи необходимо кратко фиксировать в подходящем документе.
